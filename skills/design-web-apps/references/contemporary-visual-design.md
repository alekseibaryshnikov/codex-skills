# Contemporary visual design for working apps

**Researched and visually inspected: 19 October 2026.** Use this guide with the clarity review for new apps and substantial redesigns. It addresses visual character, composition, and craft. It is not a universal 2026 style, an instruction to copy these brands, or proof that an untested interface is usable. Treat 2027 statements as forecasts.

## What this user's feedback changes

The user rejected both the original Relay/Gather examples and their clarity-oriented revisions. Treat those as rejected references. They want fresh visual design and immediately understandable UI/UX together. An ordinary dashboard shell with different colors failed; a stripped-down layout with more whitespace also failed. Do not infer that they want every app to be monochrome, sparse, table-based, or decorated with large outlined controls.

Choose visual character while resolving the task and composition. Use familiar controls in a distinctive, coherent visual system. A large calendar, image collection, map, document, or precise data grid can establish the composition through the actual work. Give a second region space when users need it, and make the relationship obvious.

### 1. Luma: expressive event identity

**Evidence:** Current [event themes documentation](https://help.luma.com/p/event-themes-and-customization), [creation workflow](https://help.luma.com/p/creating-an-event), and [developer App Store listing](https://apps.apple.com/us/app/luma-events-invites/id1546150895), accessed 19 October 2026. The listing includes an October 6 release. Web theme documentation includes paper, risograph, grain, and glass treatments; the set changes over time.

**Image inspected:** [Official mobile event view](https://is1-ssl.mzstatic.com/image/thumb/PurpleSource211/v4/55/1c/84/551c845b-eb72-c093-875c-11d1b6f83d19/4-event.png/600x1300bb.webp).

**Visible:** A large event poster, saturated surrounding color, bold title, host/date information, and a prominent white Register control. Supporting actions are quieter. This is mobile product imagery inside a promotional frame, not a verified desktop screenshot.

**Adapt:** Let recognizable content and a controlled palette give an event identity. Keep practical information and the next action consistently placed. Poster scale belongs to event detail; a timetable needs a different composition.

### 4. Float: color inside a practical schedule

## Broader 2025–2026 signals

- **Expression can support clarity.** Google's [Material 3 Expressive research account](https://design.google/library/expressive-material-design-google-research) discusses color, shape, size, motion, and containment, alongside failed experiments that removed familiar structure. These are vendor-reported studies of particular interfaces. Transfer emphasis and coherent hierarchy, not every native component or a universal performance claim.
- **Depth is selective.** Apple's [Meet Liquid Glass, WWDC25](https://developer.apple.com/videos/play/wwdc2025/219/) reserves glass principally for navigation and controls above content, and warns against glass tables or stacked glass. For web work, use clear layers and dependable reading surfaces; CSS blur does not reproduce native adaptive behavior.
- **Motion belongs in the design process.** [Figma Motion](https://www.figma.com/blog/introducing-figma-motion/), 24 June 2026, introduces a timeline and reusable motion tooling in an open-beta announcement. Treat this as evidence of investment in motion craft, not proof that animation improves every workflow.

**2027 inference:** Continued investment in visual expression, meaningful motion, content-dominant workspaces, and context-aware assistance is plausible. No source establishes one mandatory palette, layout, material, or universally dominant 2027 style. Verify changing implementation facts when they affect a build.

## Art-direction contract

Before implementing a substantial screen, write a compact internal contract with concrete decisions. Use project guidance if it already provides these. Do not make the user approve a style questionnaire or every routine choice.

| Decision | Specify | Insufficient substitute |
| --- | --- | --- |
| Main composition | Primary work surface, its proportions, and how supporting regions relate | A list of standard dashboard sections |
| Visual character | Two or three compatible qualities expressed through actual decisions | "Modern, clean, premium" |
| Typography | Family or approved system, role sizes/weights, rhythm, numeric treatment | Naming a fashionable font without hierarchy |
| Density | Typical content length, control and row rhythm, visible useful work | More whitespace everywhere |
| Color | Canvas and surface tones, action/selection roles, semantic colors, identity-bearing content | A primary hex value applied to every control |
| Geometry | Consistent corner relationships, separators, layering, icon family | Arbitrary rounded cards and shadows |
| Content | Realistic records; meaningful image or visualization treatment when appropriate | Stock metrics or imagery added to fill space |
| Behavior | Selection, expansion, editing, completion, and reduced-motion equivalents | Hover effects and a toast only |

Consider two different compositions internally, then choose against the task and references. If the user asks for research or directions first, make those references concrete before producing another full implementation. Do not assume a previous rejected composition is the starting point.

Example of sufficient direction: "A week grid takes the main screen; a narrow date/view toolbar stays above it. Quiet warm surfaces surround solid, labeled track colors. Session names use a readable medium weight, with time and room in consistent positions. Selecting a session opens an adjacent editing surface without losing the timetable. Selection and expansion use a short, consistent transition." This is a direction, not a required theme.

## Visual acceptance review

Inspect an actual render with realistic content before repeating the design across screens. Keep this gate separate from correctness and accessibility checks.

1. **Composition:** Is the principal work visually dominant? Does supporting navigation consume an appropriate amount of space? Remove repeated titles, generic welcome areas, or summary regions that displace it.
2. **Hierarchy:** Can the title, active scope, content, selection, and actions be distinguished through deliberate size, weight, position, contrast, and grouping? Avoid equal emphasis everywhere.
3. **Density:** At the same viewport and data, compare the first useful object's position, meaningful records visible, header bands, and retained context. A revision that shows less useful work needs a task-based reason. Do not optimize row count by hiding needed facts.
4. **Craft:** Inspect control heights, baseline alignment, icon weight, corner relationships, surface transitions, focus outlines, and long-content behavior. A component library supplies primitives; the finished composition still needs design.
5. **Character:** Identify what makes the product recognizable after removing its logo: content arrangement, type, color behavior, imagery, geometry, or interaction. A screen need not be loud, but it needs more than default components.
6. **Reference comparison:** Compare the intended direction and the rendered screen at a useful scale. Name observable differences. Do not describe an image as beautiful or fresh solely because a stylesheet contains attractive tokens.
7. **Responsive continuity:** Preserve the identity and primary task on a phone through recomposition. Avoid merely stacking desktop panels into a long page or shrinking type.
8. **Interaction feel:** Review selected, editing, success, and recovery states using permitted tools. A screenshot establishes only the visible captured state, not keyboard, drag, motion, or focus behavior.

Use available authorized preview capabilities. Provider-generated screenshots can support static visual inspection; interactive checks remain separate. If rendering is unavailable, complete the allowed work and state the visual evidence gap. Do not bypass access controls, invent screenshots, or report an aesthetic score as usability evidence.

Stop when concrete defects in the chosen direction and primary task are resolved. A further palette tweak is not inherently progress. When revising rejected work, explain material changes in composition, density, hierarchy, visual identity, and behavior with visible evidence.
